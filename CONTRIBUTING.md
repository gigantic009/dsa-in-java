# Contributing

Thank you for helping improve this Java DSA learning repository. Contributions should make the course clearer, more reliable and easier for learners to use.

## Before changing files

- Check the existing module structure and related guide.
- Search for a similar implementation to avoid duplicate lessons.
- Prefer a focused change over a large unrelated refactor.
- Do not copy proprietary workbook/course material, protected question-bank selections, or attribution metadata. Use public problem statements and independently write explanations and code.
- Do not invent problem IDs, platform links, company tags, complexity claims or test results.

## Java example checklist

- [ ] Clear, consistent formatting and descriptive names.
- [ ] Explain the idea and any important invariant or assumption.
- [ ] Handle meaningful edge cases.
- [ ] Use the appropriate Java standard library and avoid avoidable unsafe arithmetic.
- [ ] Include a runnable demonstration when useful; retain judge-required signatures for online-judge solutions.
- [ ] State time and auxiliary-space complexity.
- [ ] Provide sample output or tests where practical.
- [ ] Compile and test locally before claiming verification.

## Lesson checklist

- [ ] Learning objectives and prerequisites.
- [ ] Intuition and step-by-step algorithm.
- [ ] Trace or worked example.
- [ ] Correctness reasoning, invariant or proof sketch when appropriate.
- [ ] Complexity analysis.
- [ ] Practice exercises with solutions or hints separated where possible.
- [ ] Links checked and references independently written.

## Pull requests

1. Create a focused branch.
2. Describe the problem and approach.
3. List files changed and any behavior changes.
4. Record how the code was compiled/tested (and what was not tested).
5. Link the related issue, if any.
6. Keep CI green and review feedback addressed.

## Licensing and provenance

Contribute only material you are entitled to distribute. Original code and text are governed by the repository's [LICENSE](./LICENSE). Third-party content must not be copied into the repository without permission and a compatible licence; linking to an official public problem statement is preferred. Company tags should indicate a defensible association with a problem, not identify a resource provider.

## Style

Follow [Java Coding Standards](./JAVA-CODING-STANDARDS.md). For Markdown, use concise headings, descriptive links, readable tables, and avoid unnecessary decoration.
